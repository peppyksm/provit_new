## 필수 수정 사항

### 1. 정지 회원이 기존 로그인 상태로 계속 기능을 이용할 수 있음

- 근거: `backend/src/main/java/com/provit/util/jwt/JwtProvider.java:119`, `backend/src/main/java/com/provit/service/admin/impl/AdminUserServiceImpl.java:45`
- 재현: 토큰 발급 후 회원의 정지 종료일을 미래로 변경해도 `validateToken()`과 `validateRefreshToken()`이 모두 `true`를 반환했다.
- 영향: 관리자가 계정을 정지해도 로그인 중인 회원의 접근·활동과 토큰 갱신이 계속 허용된다. 로그인 함수만 정지 상태를 확인한다.
- 필요한 수정: Access/Refresh 토큰 검증에도 현재 DB의 정지 종료일을 반영해 정지 중인 회원의 인증을 거부한다.

### 2. 로그인 사용자의 스터디 목록 조회가 실패함

- 근거: `backend/src/main/resources/mappers/study/StudyMapper.xml:22`
- 재현: 실제 `StudyDAOImpl`에 로그인 회원 번호 `Long`을 전달하면 OGNL의 `value != null` 처리에서 `Long.value`의 비공개 필드 접근을 시도해 `InaccessibleObjectException`이 발생했다.
- 영향: 로그인 상태에서 스터디 목록과 참여 상태를 불러오지 못한다. 개설 자체는 성공해도 목록 새로고침이 실패할 수 있다.
- 필요한 수정: 단일 스칼라 인자의 `<if>` 조건과 바인딩을 `_parameter` 또는 명시적인 파라미터 객체로 통일한다. JVM의 접근 제한을 푸는 설정으로 우회할 필요는 없다.

### 3. 작성자가 관리자 블라인드를 수정으로 해제할 수 있음

- 근거: `backend/src/main/resources/mappers/admin-report-mapper.xml:77`, `backend/src/main/resources/mappers/post-mapper.xml:158`
- 재현: 신고를 `RESOLVED`로 처리해 블라인드한 게시글에 작성자의 일반 수정 서비스를 호출하면 제목·본문이 다시 표시됐다.
- 영향: 관리자의 게시글 차단 조치를 작성자가 우회할 수 있다. 현재는 블라인드 상태가 별도 접근 조건으로 유지되지 않고 제목·본문만 덮어쓴다.
- 필요한 수정: 서버에서 블라인드 상태를 판별하고 해당 게시글의 작성자 수정을 차단하거나 수정 후에도 비노출 상태를 유지한다.

### 4. 게시글 수정 실패 시 기존 첨부파일을 잃을 수 있음

- 근거: `frontend/src/pages/community/CommunityEdit.jsx:148`
- 코드 확인: 새 파일 업로드 후 기존 파일을 삭제하는 처리가 158행에 있고, 게시글 저장 요청은 그 뒤인 180행에 있다. 기존 파일만 제거하는 경우도 저장보다 먼저 파일을 삭제한다.
- 영향: 게시글 저장이 실패하면 DB는 기존 첨부파일을 계속 가리키지만 실제 파일은 사라진다.
- 필요한 수정: 게시글 저장이 성공한 뒤 기존 파일을 삭제한다. 저장 실패 시에는 새로 업로드한 파일을 정리하고 기존 파일을 유지한다.

### 5. 일부 인증 실패가 HTTP 200으로 전달되어 토큰 갱신이 실행되지 않음

- 근거: `backend/src/main/java/com/provit/controller/study/StudyController.java:80`, `frontend/src/api/client.js:29`
- 재현: 인증 쿠키 없는 스터디 참여 요청의 HTTP 상태는 200이고, 응답 본문에만 인증 실패 코드 318이 들어갔다. 게시글·댓글·신고·일부 관리자 API에도 같은 반환 패턴이 있다.
- 영향: 공통 Axios 처리는 HTTP 401일 때만 토큰 갱신과 재요청을 수행하므로, 해당 API에서는 인증 복구가 실행되지 않는다.
- 필요한 수정: 로그인 필요·토큰 만료에는 실제 HTTP 401, 권한 부족에는 HTTP 403을 반환하도록 통일한다. 정상 성공과 실패의 본문도 각 화면에서 올바르게 처리한다.

### 6. 운세 화면의 스크랩 표시와 알림이 서버 상태와 다름

- 근거: `frontend/src/pages/fortune/Fortune.jsx:73`, `frontend/src/pages/fortune/Fortune.jsx:368`, `backend/src/main/java/com/provit/dto/recruitment/JobScrapResponseDTO.java`
- 코드 확인: 서버의 `isScrapped`는 Boolean인데, 화면의 버튼·아이콘·알림·낙관적 갱신은 숫자 `1`과 비교한다.
- 영향: 서버에 스크랩이 저장돼 있어도 선택 표시가 꺼지고, 등록 응답을 취소로 안내할 수 있다.
- 필요한 수정: 응답과 화면 상태를 Boolean으로 통일하고, 표시·토글·알림·오류 복구에서 같은 기준을 사용한다.

### 7. 게시글 수정 화면을 새로고침하면 로그인 화면으로 잘못 이동할 수 있음

- 근거: `frontend/src/pages/community/CommunityEdit.jsx:19`, `frontend/src/pages/community/CommunityEdit.jsx:84`, `frontend/src/App.jsx`
- 코드 확인: 새로고침 직후 `AuthProvider`가 세션을 복원하는 동안 `user`는 `null`이다. 수정 화면은 인증 로딩 완료를 기다리지 않고 로그인 안내와 이동을 예약한다. 이 경로에는 `RequireAuth`도 없다.
- 영향: 이미 로그인한 사용자도 수정 URL 직접 접속·새로고침 시 편집 화면에서 이탈할 수 있다.
- 필요한 수정: `RequireAuth`로 경로를 보호하거나 `isLoading`이 끝난 후 인증 여부와 작성자 권한을 판단한다.

### 8. 화면에서 작성 가능한 긴 게시글이 DB 저장 단계에서 실패함

- 근거: `backend/src/main/resources/sql_query/schema.sql:413`, `frontend/src/pages/community/CommunityWrite.jsx:215`, `backend/src/main/java/com/provit/service/community/impl/PostServiceImpl.java`
- 재현: 한글 1,400자의 본문이 4,200바이트로 저장을 시도해 `ORA-12899`가 발생했다. 현재 본문 컬럼의 한도는 4,000바이트다.
- 영향: 화면에서는 입력할 수 있고 제출 전 안내도 없지만, 저장 단계에서 실패해 작성 내용을 저장하지 못한다.
- 필요한 수정: 지원할 본문 길이를 정하고 DB 용량과 프론트·서버 검증 기준을 일치시킨다. 한글과 Markdown 문법 길이도 포함해야 한다. 기존 컬럼을 유지한다면 바이트 한도를 검증하고, 더 긴 본문이 필요하다면 컬럼과 매핑을 함께 확장한다.

### 9. 테스트 import 누락으로 전체 백엔드 검증이 중단됨

- 근거: `backend/src/test/java/com/provit/service/document/OracleDocumentReviewPersistenceTest.java:119`
- 재현: `new Configuration(...)`을 사용하지만 `org.apache.ibatis.session.Configuration` import가 없어 전체 테스트 소스 컴파일이 실패했다.
- 영향: Maven의 테스트 컴파일 단계도 통과할 수 없어 전체 검증이 막힌다.
- 필요한 수정: 누락된 import 1개를 추가한다. 진단용 복사본에서 이 한 줄을 보완한 뒤 해당 DB 테스트를 포함한 나머지 테스트를 실행했다. 원본 파일은 변경하지 않았다.
